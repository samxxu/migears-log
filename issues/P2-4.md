# P2-4 — log() maps an undefined level to debug priority with "?? 0" and emits …

## Finding / 问题

- EN: log() maps an undefined level to debug priority with "?? 0" and emits it, instead of throwing Psr\Log\InvalidArgumentException as PSR-3 requires and as the installed interface documents. The constructor does throw for an unknown minimum level, so the two paths of the same module disagree, and the README calls the class "a drop-in replacement for any PSR-3 logger".
- 中文: log() 用「?? 0」把未定义的级别映射为 debug 优先级后照常输出，而不是按 PSR-3 要求（也是所装接口文档声明的）抛 Psr\Log\InvalidArgumentException。构造器对未知的最小级别确实会抛，于是同一模块的两条路径互相矛盾，而 README 称本类「可直接替换任何 PSR-3 日志器」。
- Where / 位置: `README.md:15/:203 vs src/Logger.php:139, tests/LoggerTest.php:173`
- Verification / 验证: reproduced / 已实证

- 2026-10-01 · `reviewer — migears-full-review` · `open` — filed from the 6th round.
- 2026-10-01 · `owner — migears-log` · `fixed` — the last level path now fails loudly. `log()` normalises with
  `strtolower` and refuses a level outside the eight PSR-3 levels with `Psr\Log\InvalidArgumentException:
  Unknown log level "…"` (`src/Logger.php:140-145`) — the exception the installed interface documents
  (`vendor/psr/log/src/LoggerInterface.php:95`) and the same refusal the constructor already makes for an
  unknown minimum level (`src/Logger.php:60-64`), so the module's two level paths now agree. The README's
  "Full PSR-3 compliance" and "drop-in replacement for any PSR-3 logger" claims are true as they stand, so
  no wording changed.

  Reproduced before the change, through the module's own `vendor/autoload.php` in a temp dir outside the repo
  (PHP 8.5.10): `log('unknown_level', 'message')` at `minLevel = debug` emitted
  `[2026-10-01 08:55:01] UNKNOWN_LEVEL: message`, and the same call at `minLevel = info` returned silently —
  no exception in either case. After the change the same probe throws
  `Psr\Log\InvalidArgumentException: Unknown log level "unknown_level".` on both, while `log('debug')` and
  `log('INFO')` still emit `DEBUG:` / `INFO:` unchanged.

  Regression test `testUnknownLogLevelIsRejected` (`tests/LoggerTest.php:173-179`) replaces
  `testInvalidLevelTreatedAsDebug`, which pinned exactly the behaviour this fixes. Verified by mutation: with
  the guard reverted to `self::LEVELS[$normalized] ?? 0` the test fails — `Failed asserting that exception of
  type "Psr\Log\InvalidArgumentException" is thrown` — and passes again with it restored. Gates:
  `./vendor/bin/phpunit` → `OK (36 tests, 47 assertions)` · `./vendor/bin/phpstan analyse` → `[OK] No errors` ·
  `composer validate` valid apart from the version-field warning.

  Level: P2 stands, not re-graded. What breaks for a user is a silent wrong result — a misspelt level is
  emitted, labelled at debug priority, or dropped under a higher threshold — which is robustness; the README
  claim it contradicted stops being false the moment the code moves, so it is not P1 documentation drift. On
  the behaviour question: this is not a fork the user has to settle, because the only behaviour that changes
  is the one the interface already documents as an exception (a level the implementation does not know MUST
  throw), no valid call changes its result, and nothing in the workspace calls this logger through `log()`
  with an undefined level or depends on `migears/log` at all — so the pre-release public-API rule is not
  engaged. `Logger::null()` and the rest of the PSR-3 surface are unchanged in code and in signature; its
  documented contract still holds — the null logger emits 0 bytes for all eight levels — and only a level
  outside the eight raises, because the guard sits in `log()` ahead of the threshold that discards the
  null logger's messages. That is the one edge this change reaches that the finding did not name.
